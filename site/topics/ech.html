Encrypted Client Hello

ECH encrypts the ClientHello — including the SNI and the ALPN list — under a public key the server publishes in DNS. It is the one feature in OkHttp that cannot be tested against a server we start ourselves: it needs real DNS, a real resolver that returns HTTPS records, and servers other people operate.

Why it lives here

A ClientHello is only meaningfully encrypted if the whole chain works end to end: the resolver returns an HTTPS record, the record carries an ech parameter, the TLS stack offers that configuration, and the server accepts it. Every link is outside the client's control, and the configurations rotate — Cloudflare publishes one at a time and rotates it hourly, honouring the previous one for a further four hours. That is a moving target no unit test can stand in for, and exactly the kind of thing this repository exists to watch daily.

ECH also has failure modes that only appear against a live server: a stale configuration earns a retry config from the server, which the client may only use after authenticating the public name against the certificate from the outer handshake, and a server offering no usable retry config securely disables ECH for that attempt. Both paths are tested against servers that deliberately serve stale and mismatched configurations.

RFC 9849 TLS Encrypted Client Hello ECH itself. Standards Track, March 2026, from draft-ietf-tls-esni. Retry behaviour is §6.1.6; authenticating the public name before using a retry config is §6.1.7.

RFC 9460 Service Binding and Parameter Specification via the DNS (SVCB and HTTPS RRs) The record type that carries the ECH configuration, the ALPN list and the address hints.
RFC 9180 Hybrid Public Key Encryption (HPKE) The construction ECH encrypts the inner ClientHello with.
RFC 8446 The Transport Layer Security (TLS) Protocol Version 1.3 ECH is a TLS 1.3 extension. A connection that negotiates TLS 1.2 cannot carry it — a case the testbed asserts rather than assumes.
RFC 8484 DNS Queries over HTTPS (DoH) How the testbed fetches HTTPS records portably, via DnsOverHttps with includeServiceMetadata(true).
RFC 8744 Issues and Requirements for SNI Encryption in TLS The problem statement ECH answers, and the attacks a naive design fails against.

Reading a result

An ECH failure has three plausible causes, and they are worth separating before filing anything upstream:

  • The resolver. No HTTPS record, or one without an ech parameter, means the client never had a configuration to offer. That is a DNS result, not a TLS one — see DNS.
  • The server. A rotated key, an expired configuration, or a changed page body will fail a test that asserts on text. Check the endpoint by hand first.
  • The client. A retry loop that does not terminate, a retry config used without authenticating the public name, or a TLS 1.2 fallback that fails instead of degrading. These are the results worth reporting.

ECH coverage in OkHttp is currently exercised by the Android instrumentation suite, which needs a platform TLS stack that implements it. The container and network suites in this repository are where the JVM-side coverage will land as it becomes runnable off-device; the status page will show those suites as soon as they exist.
